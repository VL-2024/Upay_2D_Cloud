# УПАЙ — спецификация PayTicket для бэкенда

Тот же контракт, что и для сестринской игры `Khan1_2D_Cloud` (Ордо/Чүкө) —
см. её `docs/PayTicket-API-spec-for-backend.md`. Единственное отличие —
таблица сценариев ниже (УПАЙ платит по 8 категориям, а не 5). Если один
бэкенд/эндпоинт обслуживает обе игры, `gameId` в запросе уже говорит,
какую таблицу множителей применять.

## 1. Запрос

```
GET <endpoint>?Method=PayTicket&gameId=<gameId>&amount=<amount>
```

Пример:
```
GET https://x2.kg/<путь>?Method=PayTicket&gameId=UPAY&amount=50
```

| Параметр | Тип | Обязательный | Кто передаёт | Описание |
|---|---|---|---|---|
| `Method` | string | да | игра | Всегда строка `PayTicket`. |
| `gameId` | integer/string | да | LMS (через `X2_LMS_INIT`) | ID игры, который LMS передала при старте. |
| `amount` | number | да | игрок / игра | Номинал, выбранный игроком для этого билета. |

Больше никаких query-параметров игра не отправляет (ни `currency`, ни
`language`, ни `requestId`).

Сессия/авторизация — через заголовок `Authorization: Bearer <session>`
(токен из `X2_LMS_INIT.session`), не через cookie.

## 2. Успешный ответ

HTTP 200, тело JSON:

```json
{
  "ticketId": "123456789",
  "scenario": 5,
  "win": 150,
  "balance": 1330
}
```

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `ticketId` | string/integer | да | ID билета в LMS. |
| `scenario` | integer, 1..8 | да | Номер визуального сценария (см. таблицу ниже). |
| `win` | number, ≥0 | да | Сумма выигрыша. При проигрыше — `0`. |
| `balance` | number | да | Баланс игрока **после** операции — именно это значение покажет игра, сама она ничего не досчитывает. |
| `currency` | string | нет | Код валюты, если бэкенд хочет подтвердить. |
| `currencyDisplay` | string | нет | Отображаемое обозначение валюты. |
| `multiplier` | number | нет | Множитель выигрыша для отображения. |

`denomination` в ответе не нужен и намеренно не читается — стоимость
билета и так известна игре (это `amount`, который она сама отправила).

### Таблица сценариев

| scenario | Выбито чуко | Хан | Множитель |
|---|---|---|---|
| 1 | 0 | — | ×0 |
| 2 | 1 | — | ×0,2 |
| 3 | 2 | — | ×0,5 |
| 4 | 3 (1 УПАЙ собран) | — | ×1,5 |
| 5 | 4 | — | ×3 |
| 6 | 5 | — | ×5 |
| 7 | 6 (2 УПАЙ собраны) | устоял | ×10 |
| 8 | 6 (2 УПАЙ собраны) | выбит | ×500 |

`scenario` определяет только анимацию (сколько чуко «выбивает» игрок по
ходу раунда и, при sценарии 7/8, финальный удар по Хану). Денежный
результат — исключительно поле `win`. Раунд состоит из до 7 ударов:
3 удара на 1-й УПАЙ, ещё 3 на 2-й (только если первые 3 все попали), и
финальный удар по Хану (только если все 6 предыдущих попали) — сценарий
целиком определяет исход всех ударов заранее, игра только визуализирует
их по одному.

## 3. Ответ с ошибкой

HTTP-статус, отличный от 2xx, тело JSON:

```json
{
  "code": "INSUFFICIENT_FUNDS",
  "message": "Недостаточно средств на балансе"
}
```

Игра уже умеет:
- читать `code`/`message` из тела, если они есть;
- иначе — определять код по HTTP-статусу: `401` → `SESSION_EXPIRED`,
  `409` → `INSUFFICIENT_FUNDS`, остальные не-2xx → `LMS_HTTP_<статус>`.

При ЛЮБОЙ ошибке PayTicket — оплата билета не должна списываться (или
должна быть отменена на стороне LMS), потому что клиент, получив ошибку,
откатывает списание у себя на экране.

## 4. Не относится к PayTicket, но тоже часть контракта

- `X2_LMS_INIT` (`postMessage` при старте) — баланс, номиналы, язык,
  валюта, режим REAL/DEMO. См. `LMS-Integration-spec.md`.
- Отдельного эндпоинта «получить баланс» **не существует** — баланс
  всегда приходит либо в `X2_LMS_INIT.balance`, либо в
  `PayTicket`-ответе `balance`.

## 5. Тестовый и боевой адрес

- Пока используется тот же dev-адрес, что и в контракте Khan1/Ордо, как
  заглушка для проверки GET-запроса: `https://dev.superloto.kg/api/Lotto.Users.cls`
  (см. `src/config.js` → `CONFIG.lms.endpoints.lms`).
- Прод: точный путь для UPAY не подтверждён — не угадываем его, чтобы не
  словить тихую поломку интеграции. Впишите точный боевой URL в
  `CONFIG.lms.endpoints.lms` перед реальным запуском.
